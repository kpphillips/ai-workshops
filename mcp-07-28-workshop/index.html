    Why MCP went stateless

    MODULE 01 / 11 · BASICS
    Takeaway: a legacy MCP session pins a client to one server instance for its whole lifetime, which is the entire reason sticky routing and shared session storage existed in the first place.

    Under the 2025-11-25 spec, a client sends initialize, the server hands back an Mcp-Session-Id, and every request after that must land on the exact instance holding that session in memory. Put three replicas behind a plain round-robin balancer and roughly two-thirds of a session's follow-up requests arrive somewhere that has never heard of it.

    2026-07-28 removes the pin entirely. Every request carries everything it needs: protocol version, client identity, capabilities. Any replica can answer it correctly, cold.

    the one flag that decides this 
    # v2 SDK — this is the whole difference
mcp.run(
    transport="streamable-http",
    stateless_http=True,   # any replica can answer any request
    json_response=True,
)
    // v2 SDK — Stateless defaults to true; shown explicitly
builder.Services.AddMcpServer()
    .WithHttpTransport(options =>
    {
        options.Stateless = true; // recommended default
    })
    .WithTools<MyTools>();

    The one-shot request

    MODULE 02 / 11 · BASICS
    Takeaway: every 2026-07-28 request carries its own protocol version, client identity, and capabilities in _meta, so the old two-request initialize + tools/call dance collapses into a single self-contained POST.

    This is the exact shape change Simon Willison walked through the week the spec shipped: legacy MCP needs a round trip just to get an Mcp-Session-Id before it can do anything useful. The new revision skips straight to the call.

    Header-based routing

    MODULE 03 / 11 · BASICS
    Takeaway: Mcp-Method and Mcp-Name now travel as real HTTP headers, so a gateway can route, meter, and authorize a request without ever parsing the JSON-RPC body.

    Streamable HTTP requests at 2026-07-28 must include Mcp-Method, and the three name-bearing calls (tools/call, prompts/get, resources/read) also send Mcp-Name. Your WAF or rate limiter can filter on those headers directly, with no JSON parsing and no risk of choking on a body it can't fully read.

    Illustrative middleware — not an official SDK call

    Header-based routing happens at the gateway layer, in front of whichever SDK is serving the actual MCP server, so there's no single "official" snippet for it. This is the shape of the idea, in both languages:

    gateway middleware, not the MCP SDK 
    def route(request):
    method = request.headers.get("Mcp-Method")   # e.g. "tools/call"
    name   = request.headers.get("Mcp-Name")     # e.g. "search"
    # decide the lane WITHOUT ever touching request.body
    if method == "tools/call":
        return TOOL_LANE
    return DEFAULT_LANE
    app.Use(async (context, next) =>
{
    var method = context.Request.Headers["Mcp-Method"];
    var name   = context.Request.Headers["Mcp-Name"];
    // route on headers alone — the body stream is untouched
    await next();
});

    Explicit state handles

    MODULE 04 / 11 · INTERMEDIATE
    Takeaway: dropping the protocol session doesn't mean giving up state: a tool mints a handle and the model threads it back as an ordinary argument, so state stays visible to the model instead of hidden in a session store.

    This is the pattern the maintainers point to directly: instead of a server remembering "this session has a basket," a tool returns a basket_id and the caller passes it to the next call, same as any other argument. Nothing about it is MCP-specific. It's the oldest trick in stateless API design, just newly load-bearing now that the transport can't hide state for you.

    mint the handle, thread it back 
    import secrets

BASKETS = {}  # would be a real store in production

@mcp.tool()
def add_to_basket(item: str, qty: int) -> dict:
    """Add an item and return the handle for later calls."""
    basket_id = "bk_" + secrets.token_hex(4)
    BASKETS[basket_id] = {"item": item, "qty": qty}
    return {"basket_id": basket_id, "item": item, "qty": qty}

@mcp.tool()
def checkout(basket_id: str, confirm: bool = True) -> str:
    """Finish the order — basket_id came from add_to_basket."""
    basket = BASKETS.get(basket_id)
    if basket is None:
        return f"No basket found for {basket_id!r}."
    return f"Checked out {basket['qty']}x {basket['item']} ({basket_id})."
    static readonly ConcurrentDictionary<string, Basket> Baskets = new();

[McpServerTool, Description("Add an item and return the handle for later calls.")]
public static object AddToBasket(string item, int qty)
{
    var basketId = "bk_" + Guid.NewGuid().ToString("N")[..8];
    Baskets[basketId] = new Basket(item, qty);
    return new { basket_id = basketId, item, qty };
}

[McpServerTool, Description("Finish the order — basketId came from AddToBasket.")]
public static string Checkout(string basketId, bool confirm = true)
{
    if (!Baskets.TryGetValue(basketId, out var basket))
        return $"No basket found for {basketId}.";
    return $"Checked out {basket.Qty}x {basket.Item} ({basketId}).";
}

    Set an item and quantity, then run both calls. The handle minted by the first call should be the exact string passed into the second.

    Cacheable list results

    MODULE 05 / 11 · INTERMEDIATE
    Takeaway: tools/list, prompts/list, resources/list, and resources/read now carry ttlMs and cacheScope, so a client can hold a tool catalog instead of re-fetching it on every reconnect.

    A server that sends no cache hints, which describes every pre-2026 server, looks exactly like a client that never caches. Nothing regresses; you only get faster reconnects when a server opts in.

    Illustrative — wire shape, not a verified exact API signature

    Both SDKs let you set these per-operation (Python: cache_hints= on the method registration; C#: per-operation cache metadata), but this is the field shape that actually crosses the wire, true regardless of which SDK produced it.

    tools/list result, 2026-07-28 
    {
  "jsonrpc": "2.0", "id": 7,
  "result": {
    "tools": [ {"name": "search", "...": "..."} ],
    "ttlMs": 30000,
    "cacheScope": "shared"
  }
}

    Multi-Round-Trip Requests

    MODULE 06 / 11 · ADVANCED
    Takeaway: with no server-initiated channel left, a tool that needs something from the user returns resultType: "input_required" instead of pushing a request. The client answers and retries the exact same call with the answer attached.

    Legacy MCP let a server reach back into an open connection and ask the client a question mid-call. 2026-07-28 has no such connection to reach through. MRTR turns the interaction around: the call itself becomes the question, and the retry becomes the answer.

    one tool body, both eras — from the official SDK docs 
    class Quantity(BaseModel):
    copies: int

async def ask_quantity() -> Elicit[Quantity]:
    """Resolver: ask the user how many copies to put aside."""
    return Elicit("How many copies?", Quantity)

@mcp.tool()
async def reserve(
    title: str,
    quantity: Annotated[ElicitationResult[Quantity], Resolve(ask_quantity)],
) -> str:
    """Reserve copies of a book, asking the user how many."""
    if isinstance(quantity, AcceptedElicitation):
        return f"Reserved {quantity.data.copies} of {title!r}."
    return "Nothing reserved."
    [McpServerTool, Description("Reserve copies of a book, asking the user how many.")]
public static string Reserve(
    McpServer server,
    RequestContext<CallToolRequestParams> context,
    string title)
{
    if (context.Params!.InputResponses?.TryGetValue("copies", out var response) is true)
    {
        var copies = response.Deserialize<int>();
        return $"Reserved {copies} of \"{title}\".";
    }

    if (!server.IsMrtrSupported)
        return "This tool requires MRTR support (2026-07-28).";

    throw new InputRequiredException(
        inputRequests: new Dictionary<string, InputRequest>
        {
            ["copies"] = InputRequest.ForElicitation(new ElicitRequestParams
            {
                Message = "How many copies?",
                RequestedSchema = new() { Properties = { ["copies"] = new ElicitRequestParams.NumberSchema() } }
            })
        },
        requestState: "awaiting-copies");
}

    Lab: step through the input_required round trip

    Call reserve() first. The server can't finish because it doesn't know how many copies, so it comes back asking instead of failing.

    The extensions framework

    MODULE 07 / 11 · ADVANCED
    Takeaway: capabilities like Tasks and MCP Apps are opt-in extensions identified by reverse-DNS IDs and negotiated per request, so the core spec doesn't need to grow every time the ecosystem does.

    A client declares the extensions it supports in _meta.io.modelcontextprotocol/clientCapabilities.extensions on every request. A server that can't do without an extension the client didn't declare returns -32021 Missing Required Client Capability instead of silently degrading.

    how a client declares support 
    {
  "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": {
    "name": "generate_report",
    "arguments": { "quarter": "Q3" },
    "_meta": {
      "io.modelcontextprotocol/clientCapabilities": {
        "extensions": {
          "io.modelcontextprotocol/tasks": {},
          "io.modelcontextprotocol/ui": {}
        }
      }
    }
  }
}
    In each SDK

    C# ships Apps and Tasks as separate opt-in packages, .WithMcpApps() and .WithTasks(new InMemoryMcpTaskStore()), bolted onto the base SDK rather than baked in. Python declares extension support through its own extensions API (see the rail link); the wire shape above is what both ultimately produce.

    Tasks: long-running work

    MODULE 08 / 11 · ADVANCED
    Takeaway: a tool that can't finish inside one request returns a task handle instead of blocking, and the client polls tasks/get, and can tasks/cancel, until the real result is ready.

    Tasks graduated out of the experimental core into the io.modelcontextprotocol/tasks extension at 2026-07-28. The task is durably created before the response is sent, so a client can disconnect and come back later with the same taskId.

    Honest gap — not just a rail footnote

    As of this release, the Python SDK does not implement Tasks yet. It shipped removed outright from v2, with the note that 2026-07-28 "moves tasks out of the core protocol and into an official extension, which this SDK does not implement yet." The lab below runs at the raw JSON-RPC level for that reason, not through @mcp.tool() decorators. C# has it as an opt-in package.

    MCP Apps: inline UI

    MODULE 09 / 11 · ADVANCED
    Takeaway: a tool can point to a ui:// resource instead of returning plain text, and the host renders it in a sandboxed iframe that talks back over the same JSON-RPC channel, so a chat turn can become a live chart the user actually clicks.

    The View (the iframe) behaves as its own MCP client; the Host is a proxy between it and the real server. Only the parameters of a UI-initiated tool call ever reach the model; the rendered HTML itself never does.

    the four-step sequence from the ext-apps spec 
    // 1. Discovery — tools/list carries UI metadata
// 2. Initialization
{"method":"ui/initialize"}  →  {"hostContext":{...},"capabilities":{...}}
// 3. Data delivery — host pushes tool data into the iframe
{"method":"ui/notifications/tool-result","params":{"content":[...]}}
// 4. Interactive phase — a click inside the iframe calls back out
{"method":"tools/call","params":{"name":"drill_region","arguments":{"region":"west"}}}

    Auth hardening

    MODULE 10 / 11 · ADVANCED
    Takeaway: authorization servers now return iss per RFC 9207, and a client must validate it before redeeming a code, closing an authorization-server mix-up hole that isn't exotic: just the same defense OAuth/OIDC has used for years.

    A mix-up attack tricks a client into redeeming a code meant for one authorization server against a different one. Checking that the iss on the callback matches the authorization server the client actually started the flow with closes that hole. The spec also formally deprecates Dynamic Client Registration in favor of Client ID Metadata Documents (CIMD): static, URL-based, nothing to register at runtime.
