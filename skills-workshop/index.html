Skills that stay true

A skill is one short file of instructions that an AI agent loads when a task matches. It only helps while it still helps. You will write one small skill, then build the test that tells you whether to keep it after the next model update.

Quoted published by the linked source Derived computed on this page Illustrative demo data, not measurements Your run a live call you paid for Convention this workshop's choice, not a spec

Every module is a lab: you do one thing, read a result, move on. There are no quizzes and nothing is scored. Labs run in demo mode, with canned replies labelled illustrative, until you connect an OpenRouter key in the Live labs panel (right rail; at the bottom on phones). Demo mode teaches every lab. Live mode makes the numbers yours.

1. Keep SKILL.md short and the rest one level down

An agent loads a skill in steps: name and description at startup, the whole SKILL.md when a task matches, extra files only when needed. The spec asks for a SKILL.md under 500 lines and a body under about 5,000 tokens Quoted. Those are ceilings. Every line you keep is paid for on every activation.

2. Give each step the freedom it deserves

Anthropic's guide matches specificity to fragility Quoted. High freedom is goal text, for steps with many valid answers. Medium is a template or pseudocode, for a preferred pattern. Low is an exact script, for fragile steps where consistency matters. Choosing too tight wastes the model; choosing too loose gives you variance.

Pick a level for each step

Do it yourself

For each step, ask: if this goes slightly wrong, what breaks, and how many valid answers are there? Pick a level and read the SKILL.md text it would produce. Nothing here is scored; the usual starting point is one click away.

Same step, three freedoms, many runs

Test it yourself

The step is the Done when line. A script then checks one rule: a single line shaped like Done when: ... (check: ...). Run it at each freedom and compare how many outputs pass and how many different outputs you get.

The three wordings

A chat call cannot run scripts, so the low-freedom wording here is the nearest chat equivalent: a fixed sentence with one blank. In an agent with a shell, low freedom means "run this script", as in Anthropic's database-migration example.

3. Write the frontmatter once, not once per model

A skill has one SKILL.md and one frontmatter block, not a copy per model. The Agent Skills spec requires name and description. Optional fields are license, compatibility, metadata and allowed-tools Quoted. A list of models to test is not a field.

Where the test list goes Convention The spec defines metadata as arbitrary string keys to string values. This workshop puts the OpenRouter slugs in metadata.openrouter as one comma-separated string, and the local model in metadata.local. That is our convention, so your eval script has one file to read; no tool requires it. Claude Code's own model key is different: it picks one model for the turn while the skill is active. It is not a test list.

4. Author three cases before you run anything

Anthropic says to build evaluations first, and agentskills.io says to start with two or three cases Quoted. A case is a realistic prompt, a way to grade the output, and (for this workshop) a flag for the held-out slice. Include one case the skill must not trigger on, or you will only learn that it works when it should.

5. Run each case many times, with and without the skill

One good output is an anecdote. Run every case many times per model, grade each output, and report the percent passing with its counts. Do it twice, once with the skill loaded and once without, and compare. Checkable outputs get a script grader first.

6. Judge what a script cannot check, and audit the judge

Some qualities have no script: is this "done" line checkable, did the reply invent a fact. Use a judge model for those, and never the model under test. A judge label is another model's opinion, not ground truth, so read a sample yourself.

Write the judge prompt and run it

Test it yourself

The question for each case comes from the case's rubric in module 4. The judge replies with JSON. Rows whose model under test is the primary judge use the fallback judge instead.

Audit six judge labels

Do it yourself

Draw six judged rows, favoring ones where the script and the judge disagree. Read each output and the judge's reason, then mark whether you agree. This counts your disagreements with the judge. It is not a score for you.

7. Keep the rows, and hold a slice out

Each run leaves a row: the prompt, the model, the output, the grader and the pass or fail. Keep them. Rows like these could later become supervised fine-tuning data for an open model. This workshop does not fine-tune. It teaches you to keep the data so that a later fine-tune is possible, and to keep a held-out slice the judge labels but that never goes into training, so you can still measure honestly.

Split and export

Do it yourself

The split is by case, not by row, because runs of the same prompt would leak. Set the held-out flag on cases in module 4. With three cases, one held out is a third; with dozens, a fifth is more usual.

8. Decide: keep the skill, or cut instructions

Write the rule before you look at the numbers. This workshop's rule Convention: keep the skill only if the pass rate holds. If a stronger model does worse with the skill than without it, cut instructions. Anthropic's guide tells you to test on every model you plan to use, asks of its strongest tier "does the Skill avoid over-explaining?", and warns that what suits one model may need more detail for another Quoted. agentskills.io adds that when pass rates plateau, try removing instructions and see if results hold or improve Quoted.

9. Re-run when the models change, and once a month

None of the official skill docs we read sets a retest calendar for skills, and Anthropic's guide says there is no built-in way to run evaluations and that you build your own Quoted. So the cadence is yours. This workshop's version Convention: re-run the same cases whenever any model id in metadata.openrouter changes, and once a month if nothing changed.

    Limits to carry with you

    What this workshop cannot tell you
    • There is no official retest calendar for skills. The re-run triggers here are a convention.
    • Judge scores are not ground truth. A judge is another model with its own habits, and it can be wrong in the same direction on every run. Read samples.
    • The eval loads SKILL.md into the system prompt. It does not test whether an agent product would choose to activate the skill from its description. That is a separate test (see agentskills.io on optimizing descriptions).
    • Three cases and a handful of runs is a smoke test. The interval beside each percentage shows how little it settles.
    • Demo mode is canned and deterministic. Its numbers teach the method and say nothing about any model.
