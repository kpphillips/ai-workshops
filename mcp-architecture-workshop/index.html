MCP architecture

Model Context Protocol revision 2026-07-28 is a stateless JSON-RPC 2.0 protocol: a host application creates one client per server, and that server exposes context and tools. This page follows the specification and docs on modelcontextprotocol.io as checked on 16 Nov 2026, using a fictional scheduling assistant called Hearth and a mock server named jobs.

Tools, resources, and prompts

A server can offer three primitives, and the specification gives each a different control model: tools are model-controlled, resources are application-driven, and prompts are user-controlled. Hearth's jobs server uses all three for scheduling, without the protocol telling the host which screen to build.

JSON-RPC messages

Revision 2026-07-28 removed the initialize request and the notifications/initialized notification; every request carries its protocol version and client capabilities in _meta, and server/discover is the optional way to read the server first. tools/list and tools/call are separate requests, and servers do not open their own JSON-RPC requests.

    stdio and Streamable HTTP

    Both standard transports carry the same JSON-RPC messages; stdio frames them as newline-delimited JSON on a subprocess, and Streamable HTTP sends each message as its own POST to one endpoint. Authorization, cancellation, and logging are what change, not the method names.

    Authorization

    Authorization is optional, and the specification defines it for HTTP transports: the MCP server is an OAuth 2.1 resource server, the client requests access tokens, and an authorization server issues them. A stdio server should take credentials from the environment instead of that OAuth flow.

    Trust boundaries

    The specification requires hosts to get explicit user consent before data leaves or a tool runs, and it says the protocol cannot enforce that consent by itself. Tool descriptions and annotations are untrusted unless they come from a server you trust, because a tool is arbitrary code execution.
