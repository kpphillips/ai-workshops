Agent harnesses vs. software factories

A model is not an agent, and an agent is not a factory. Seventeen modules in seven parts take you from a bare model to a hardened deploy, and each one pairs an in-page lab with a lab in the starter repo.

Every lab here runs in demo mode with no key. Live labs call OpenRouter once you connect a key in the Live labs panel (right rail; at the bottom on phones). Nothing is scored and there are no quizzes: facilitator prompts sit between the parts.

    Facilitator prompt

    Is the harness dead?

    Thesis

    Labs train models on harness traces, so coding skill moves into the weights and harnesses converge. Theo's rough guess is a 3 to 5% gap between Claude Code and Codex when running Codex models (Quoted informal, [00:44:48] in his video).

    Counter-thesis

    Prompts and shims shrink, but sandboxes, persistence, subscriptions, permissions, cache efficiency and multi-agent coordination matter more (Jediah Katz, Harrison Chase).

    • Which guardrails ("shims") in your workflow exist only because of an older model, and which are permanent infrastructure?
    • The measured figure is HarnessTax, covered in module 13, not the 3 to 5%.

    Facilitator prompt

    Dark factories vs. human-aligned factories

    Lights off

    Dan Shapiro's "dark factory", popularized by StrongDM: humans neither write nor review code, and put their effort into specs, scenario environments and the outer and meta loops (StrongDM, Shapiro).

    Lights back on

    Models trained on short pass/fail tasks optimize for passing tests, so brownfield systems decay without humans steering Program Design (Dex Horthy).

    • Where should humans sit: reviewing huge diffs after the fact, or specifying types and signatures before the harness runs?
    • Where is your biggest bottleneck: the inner loop (agents fail to one-shot), the outer loop (PR review) or the meta loop (the same mistakes repeat)?

      17. Docker, compose and a VPS

      Part 7: Ship it

      Model-generated code runs in a locked-down container, and API keys stay in the harness process outside it. Build the run command flag by flag and see what each missing flag leaves open.

      Harden the sandbox

      Toggle and generate

      Flags: docker run reference (Quoted). Never mount the Docker socket into the agent container; per Docker's security docs only trusted users should control the daemon. The compose file is a sketch: the repo's own file is the tested one.

      VPS notes

      Quoted
      • Run Docker rootless on the host.
      • Optionally add the gVisor runsc runtime, an application kernel in userspace (quick start).
      • Docker Sandboxes (sbx) run a microVM with its own kernel, but need KVM, which most cheap VPSes lack (isolation docs).
      • Package installs need egress: use a separate allowlisted-proxy phase, and keep the sandbox default at --network none.
      Build it in the repoRun your loop's tool execution in a hardened container, then deploy the compose stack on a VPS.
